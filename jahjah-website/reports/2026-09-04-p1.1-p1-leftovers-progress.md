**THE LANE HAS NO KNOWLEDGE OF THE BUDGET IT SPENDS.** Both dispatch lanes and every interactive
session on the box draw on one Claude Max 5-hour window. `web-dispatch.sh` caps chunks per day and
`run-chunk.sh` caps wall-clock at 7 h, and neither is the constraint that actually binds. A chunk
started late in a window is guaranteed to die mid-flight, and nothing in the lane can see that
coming.

WHY NEITHER RUN LEFT A REPORT. `run-chunk.sh` invokes `claude -p "$(cat "$BODY")" … | tee -a "$LOG"`
with the default `--output-format text`, which emits only the FINAL assistant message. A run that
dies on the usage limit has no final message, so nothing is emitted — 88 minutes of #24's work
produced 53 bytes. `tee` captured everything there was to capture; the transcript never existed on
stdout.

NOT THIS REPOSITORY. Checked and cleared: `.claude/settings.json` contains `permissions` only, no
`hooks` key; there is no hook registered at project or (per the shared-box rule) user level; the

PROPOSED UNIT CHANGE — FOR THE ERP SIDE, NOT MADE HERE
(`infra/vps/web-dispatch/run-chunk.sh` and `web-dispatch.sh`; both lanes share the code, D230)

(a) CAPTURE THE TRANSCRIPT. Run `claude -p … --output-format stream-json --verbose` and tee that.
    A dispatched chunk that dies would then leave evidence instead of one line. The log is already
    mode 600 in a mode-700 directory and never published, so this changes no exposure — it makes
    that existing property load-bearing, which it should have been from the start.

(b) A USAGE-LIMIT EXIT IS RETRYABLE, NOT A CHUNK FAILURE. Detect it (`grep -q "hit your session
    limit" "$LOG"` after the run) and branch:
      · restore `chunk:approved` and remove `chunk:running` — add before remove, as everywhere else
        in this codebase — instead of marking `chunk:failed`, so the next poll re-dispatches;
      · do not call `jj_note_failure` — a shared-pool exhaustion is not a lane fault;
      · refund the daily-cap slot (`count-$JJ_TODAY` was incremented at dispatch; #36's dead 523 s
        consumed one of three for 2026-09-04);
      · comment the reset time on the issue — the log already carries it verbatim;
      · optionally write `state/pool-blocked-until` from that reset time and have the poll skip
        until it passes, so the lane does not spend 2-minute polls walking into a wall.

(c) SECONDARY, AND IT UNDERMINES OWNER LAW 2: THE THREE-STRIKE SELF-DISABLE CANNOT FIRE FOR A CHUNK
    FAILURE. `jj_note_failure` runs in step 0 of a poll (settling the previous chunk); that same
    poll then finds nothing approved and calls `jj_finish_ok`, which writes 0 back to
    `consecutive-failures`. Measured, one second apart, in web-dispatch.log:

      15:52:04Z ERROR failure 1/3: chunk #36 exited 1 after 523s
      15:52:04Z INFO  clean run — consecutive-failure counter reset from 1 to 0

    Three chunk failures in a row can never accumulate, because a chunk failure is always booked by
    a poll that goes on to be idle. The counter today reads 0 with two dead chunks behind it. The
    fix is for the settle-step to return before `jj_finish_ok`, or for the idle path not to reset a
    counter it did not earn. Worth taking with (b): once (b) stops booking pool exhaustion as a
    failure, the law would be free to mean something again.
