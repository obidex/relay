## 3. The review found more than the SQL

Four-agent panel, two rounds, **no blocker and no high in round 2.** The one-line `ALTER TABLE` was
correct from the start. Everything the panel caught was in the *prose around it* — which is the part
that tells the next person what is true.

- **Three canon files still described the change as unshipped**, including the file the contract makes
  a mandatory pre-read for this module. One of them pointed a future contributor directly at the
  regression the change guards against. This is the `D211` failure mode, and I had introduced it in
  the same commit that corrected another instance of it.
- **My own migration comment stated a residual backwards** — claiming a restore path would now be
  refused, when in fact it silently *undoes* the promotion. Two seats caught it independently. **I
  verified it empirically rather than taking their word**, which was right: their shared account of
  the mechanism was correct, but the privilege it needs was not, and a third measurement split it into
  two forms with two different gates.
- **The migration was already applied, so the wrong comment was NOT edited.** The contract is explicit
  that a wrong comment in an applied migration is corrected by a superseding record, never by an edit,
  so the repo copy stays byte-identical to what actually executed. The correction lives in the
  judgment register and in two non-public files. **The obligation this leaves — a superseding comment
  inside the migrations folder — is recorded and booked against the next migration**, rather than
  quietly dropped.
- **One panel recommendation was wrong and would have broken the gate.** A seat proposed placing the
  new probe where it would run as an actor that *cannot* perform it in the throwaway environment. I
  wired it that way, the build went red for a reason unrelated to the property being guarded, and I
  moved it to the correct actor. *A panel recommendation is a lead, not a patch.*
- **A seat caught that I had put sensitive detail on the wrong side of a boundary.** Several repo
  files are served publicly and unauthenticated from the production domain; the module pitfall files
  are deliberately excluded. I had written the full mechanism into a file that IS served. It is now
  trimmed to decision-and-trigger, with the mechanics only in the excluded files. **The same mistake
  is in the preflight report published earlier in this chunk**, which is world-readable; that file has
  now been trimmed too, though git history is permanent and the earlier revision cannot be recalled.
  Practical exposure is low — every path needs privileges an attacker holding them has already won —
  but the rule is about where this class of content lives, and I broke it before checking.

## 4. Recorded, not fixed

- **`D215` (OPEN, priority):** the equivalent guards on the payment path were not promoted alongside
  the anchor. Closing it needs new schema SQL and therefore re-crosses the approval gate, so it was
  **not** applied in the chunk that found it. The entry carries the full matched-pair inventory —
  including two test files that would silently undo that promotion — so it cannot ship half-done.
- **Both entries scope the gain honestly as auditability, not access reduction.** The set of actors
  who can reach the anchor did not shrink; what changed is that one silent route is now a noisy one.
  A seat caught that the follow-up entry had inherited the very over-claim the main entry was written
  to correct, which would have sent the next rotation through an approval gate on a false premise.
- **The dispatch lane binds no model**, so the routing table does not govern what a dispatched job
  runs on. Recorded in the infrastructure pitfalls file; not changed, because that lane is out of
  scope for this chunk.
