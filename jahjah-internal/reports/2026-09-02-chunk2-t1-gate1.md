## 2. The two naming decisions, and why they differ

**RENAMED: the guard function → `sale_issue_within_dispatch()`.** The paste delegates trigger and
function naming explicitly. Measured against the live catalog: **no function in this schema carries a
`jhx_` prefix** — none of them — while **42 of the 115 triggers share their function's name**, which
is the house convention for a dedicated trigger function. Naming it after its trigger follows the
convention; the prefix follows nothing.

**KEPT: the column `dispatch_item_id`.** The table's three sibling links are `source_shipment_item_id`,
`source_sales_order_item_id` and `source_sales_return_item_id`, so `source_sales_dispatch_item_id`
would be more consistent, and the design entry originally called it that. **I did not rename it.** The
naming question was raised in the previous attempt's report, the approving paste came back with the
column name unchanged, and the delegation covers trigger and function names only. Overriding a name
the owner had in front of them would be substituting my judgement for a decision they had the chance
to make. **Recorded as a follow-up instead** — renaming after apply costs a second migration, so it is
worth deciding once rather than twice.

## 4. The sweeps the canon requires, done before applying

- **Foreign-key/embed sweep.** Part (c) adds the first foreign key between the ledger and the dispatch
  lines. The one app embed of that parent resolves from a *different* table and via a different key,
  so it is untouched; the new key makes a ledger-to-dispatch embed newly **resolvable**, never

- **Collateral sweep for a new always-on trigger.** Fourteen files write to the ledger. The trigger
  and the CHECK fire **only** on `sale_issue`, which narrows collateral to **one site**: the dispatch
  suite's hardening test asserts that a raw issue row *without* a dispatch line is accepted. **Part
  (c) deliberately ends that**, so the assertion is being updated to the new, stronger contract — the
  negative half of that test is kept and a new rejection case is added. Nothing is weakened to go
  green. The demo seed writes only an opening balance, and the other two sales suites reach the
  ledger through the RPC, so neither is affected.
- **Writer sweep.** `dispatch_sales_order` is the only writer of issue rows in the entire schema; the
  generic ledger writer refuses the type outright and the moving-average function only reads it.
