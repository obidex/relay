## 3. What it actually buys — and getting that wrong three times

**This is the part worth reading.** Three drafts of the canon were wrong in sequence: it **overstated**
(claiming a receipt now lands with its audit trail), then **over-corrected** (claiming the UPDATE side
was untouched), then **overstated again** (claiming the INSERT path closed). Each was caught by the
panel and each was checked by measurement rather than accepted on the reviewer's word — which mattered,
because one of my own "confirming" measurements was itself wrong (an arithmetic slip made a control
look present when it was my test that failed).

**Every error was in a summary sentence. None was in a measurement.** So the summary is gone; the
module file now carries a table of measured outcomes and the register points at it.

- **Genuinely closed:** the rate bound, the operating-currency rate pin, and the rate/denomination
  freezes on UPDATE — all now enforced in system context. The denomination restatement vector was
  wide open before.
- **Still open, and this is the half that matters:** a *self-consistent* fabricated receipt on a
  **non-operating** currency books an arbitrary figure with **no audit row**. Measured accepted before
  the change too, so it is **pre-existing and not introduced here** — but it is precisely why "the
  money half is closed" was never a true sentence. It is `D161` territory, and `D161` had already
  named the exact residual before I measured it.
- **Widened:** an internally inconsistent forgery that the deterministic constraint used to refuse is
  now silently normalised into a valid row. Not a new capability — the self-consistent form was always
  accepted — but one fewer speed bump, on both verbs.

**The generalisation, now the third instance in three chunks:** a change's blast radius gets measured
because it is frightening; its *value* gets asserted because it is pleasant. Enumerate the sub-cases —
operating vs non-operating, INSERT vs UPDATE, actor vs no actor — and measure each before writing one
sentence about what a hardening change buys.

## 4. Two pins, and what each can physically see

`replay-check.sh` pins from scratch, and **that lane never runs the suites**, so it covers
migration-side regressions only — the round-1 version of its comment claimed more. The live-side pin
(block `10g`) covers the regressions that actually happen on the shared database. Neither substitutes
for the other, and `10g` runs *before* the two suites it relates to, so it catches a stranded
downgrade on the **following** run. That is weaker than it sounds and is written down rather than
implied.

The probe grew four arms, each sabotage-verified: it asserts the audit row's **figure** rather than
its existence; a **no-actor** arm pins the open residual, with a failure message pointing at that
residual's own closure so that fixing it tells the next person to delete the arm rather than weaken
it; and two arms cover **both** halves of the freeze, the denomination half being the more dangerous
one since flipping it re-derives against a different scale.

## 3. Two traps found while writing the probe, either of which would have made a future test lie

**The audit trigger writes nothing when there is no actor.** It opens by returning early if there is
no authenticated user. So an audit assertion made without setting an actor fails *while the guard is
working perfectly* — it proves the opposite of what it claims. My first probe did exactly that, and
the failure looked like a broken migration.

**The platform's own identity helper is not the same function in the two lanes.** The throwaway
container ships an older implementation that reads one setting; the live project has a newer one that
also reads another. Every committed suite sets the newer one — correctly, because those suites run
against live — but in the bootstrap lane that silently leaves the identity NULL. Anything that must
work in both lanes has to set both.

**This is the "which database does the control run against?" question one level deeper:** not only
which database, but **which version of the platform's own helpers it gets there.** A suite that is
correct in one lane can be quietly inert in the other, with no error to show for it.

## 4. A near-repeat of chunk 1's incident, caught by design this time

The probe writes a payment. My first version let it commit, on the reasoning that the container is
thrown away afterwards — **which is the same "it's only a probe" reasoning that put two unapproved
indexes on the live database in chunk 1.** It now rolls itself back explicitly, and the report of that
earlier incident is cited in the code comment so the next person meets the lesson where the temptation
is, not only in the register.
