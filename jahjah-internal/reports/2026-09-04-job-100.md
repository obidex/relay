## The cause, in one sentence

**Chunk #97 hit the account's five-hour usage cap (HTTP 429, `"error":"rate_limit"`,
`"overageStatus":"rejected"`) at 21:40:38Z — seven seconds after it had finished writing a complete
44,286-byte report to `/root/jahjah-internal/.panel/chunk6-BLOCKED.md` and passed that report's
secret scan, i.e. one tool call before `publish-report.sh` would have run — so the chunk's work was
not lost, only unpublished.**

Two things are being conflated in the issue's framing, and they need separating:

| | |
|---|---|
| **Why the chunk did no engineering work** | It **stopped on purpose** at preflight. A *dispatched* session has no database lane: `psql` and `pg_dump` are refused with nobody to approve them, and `SUPABASE_ACCESS_TOKEN` is absent, so `scripts/db-query.mjs` exits 1. The chunk measured both, declined to route around either, and wrote a blocked report. That is the correct behaviour under `D228`. |
| **Why nothing was published** | The usage cap, 7 seconds later. Unrelated to the stop. The chunk was mid-publish when the API started returning 429. |

So the honest verdict is: **the chunk succeeded at the only thing it could do, and then died on the
doorstep.** `exit 1` and `chunk:failed` describe the process, not the work.

### Three lane findings this postmortem produced

**A — the lane dispatched into an almost-empty quota window and had no way to know.** The exhausted
five-hour window opened at **19:30Z**. Chunk #96 started at **20:23:09Z** and ran **3,406 s** (57 min)
on `opus`/`xhigh` — inside that window. Chunk #97 was dispatched **7 minutes 13 seconds later**, at
21:27:08Z, into whatever was left, and consumed it in 13m34s. `web-dispatch.sh` has a daily-count cap
and a per-chunk timeout but **no quota preflight and no 429 handling** — a chunk that dies this way is
indistinguishable, to the lane, from one that crashed.

**B — the three-strike breaker cannot trip on a chunk failure.** Look again at 21:41:04Z: the same
poll books the failure and then erases it, in the same second.

```
2026-09-03T21:41:04Z ERROR failure 1/3: chunk #97 exited 1 after 810s
2026-09-03T21:41:04Z INFO  clean run — consecutive-failure counter reset from 1 to 0
2026-09-03T21:41:04Z INFO  done in 0s — idle — nothing approved
```

The mechanism: `web-dispatch.sh:207` calls `jj_note_failure` while settling the previous chunk, which
increments `consecutive-failures` to 1 (`jahjah-common.sh:290`). The **same** poll then finds nothing
approved and ends with `jj_finish_ok`, whose first act is `echo 0 > "$JJ_STATE/consecutive-failures"`
(`jahjah-common.sh:299–302`). On-disk state today is `0`. So **three consecutive chunk failures would
never trip `JJ_FAILURE_CAP`** — each is wiped by its own poll's idle success before the next one
arrives. The code comment at `web-dispatch.sh:199–203` anticipates a *related* double-booking race but
not this one. This is a live hole in the lane's safety net, found incidentally; it is not chunk 6's
problem and should be fixed on its own ticket.

**C — a dispatched chunk's console log is not a work log.** 810 seconds and 100 tool calls produced
three lines of stdout, because `claude -p` emits only a final result. When the final result is an API
error, the entire run is unobservable from `chunks-erp/<n>.log`. The recoverable record was the
JSONL transcript and a gitignored scratch file — neither of which the lane knows about. Any future
"why did a chunk die" question hits this same wall unless the lane captures more.
