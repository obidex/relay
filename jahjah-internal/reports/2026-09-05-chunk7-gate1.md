## The backup and the apply lane

1. `pg_dump --schema=public` to `/root/backups/pre_20260905120000_d234_ledger_bindings_20260905.sql`,
   verified non-empty and containing `CREATE TABLE`, size reported — **before anything else**.
2. **`node scripts/db-query.mjs --migration` is the documented command and is not runnable on this
   box**: `.env.local` carries no `SUPABASE_ACCESS_TOKEN` (variable **names** were read; no value
   was). The chunk plan named the fallback, which is `backup.md` §3's wrapped form and is what
   chunk 6 used for the same reason:

   ```
   psql -1 -v ON_ERROR_STOP=1 \
        -f supabase/migrations/20260905120000_d234_ledger_bindings.sql \
        -c "insert into supabase_migrations.schema_migrations (version, name)
            values ('20260905120000','d234_ledger_bindings');"
   ```

   `-1` is load-bearing, not a detail: it puts the migration **and** its version row in ONE
   transaction. A bare `-f` is autocommit statement-at-a-time, which is how two unapproved indexes
   once reached the live database (`D219`). The file is named by literal path so the hook hashes
   the exact bytes that will run; its check is content-based, so this lane is covered identically
   to the helper's.

**If the hook refuses after this report lands, the chunk STOPS and reports.** There is no override
and no workaround.
