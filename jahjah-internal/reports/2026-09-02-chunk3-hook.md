## What it does

A `PreToolUse` hook on `Bash`. It reads the command, and if the command applies a database
migration it refuses to let it run unless that file's SHA-256 is already published on the relay's
`origin/main`, inside a report under `jahjah-internal/reports/`.

`D223` made a blocked task carry its SQL. This makes the reverse impossible too: **SQL that nobody
published cannot be applied.** "I'll publish the report afterwards" stops being available.

**User scope, so it also applies in `-p` mode** — which is the mode that matters, because that is
how the dispatch lane and the coming inbox lane start work.

## What it does NOT buy

Stated plainly, because a gate trusted for more than it does is worse than no gate:

- **It compares bytes, not meaning.** The identifier rule and the owner's confirmation still decide
  what the bytes may be. A published-and-approved hash is not a correct migration.
- **It removes accidents, not adversaries.** A hostile session could publish a report first and then
  apply.
- **It matches the HOUSE apply forms.** SQL pasted into a heredoc, or copied into a temp file outside
  `supabase/migrations/`, is not seen. `docs/runbooks/backup.md` §3 applies the file **verbatim, by
  path**, which is exactly what this covers — but the gap is real and named here rather than left to
  be discovered.
- **It fails OPEN on an unparseable payload**, logging `PARSE`. Every `Bash` call on this box goes
  through this hook; failing closed on a payload it cannot read would brick every session on the
  machine, including the one that would be used to fix it. A migration apply is a recognisable shape
  and an unreadable payload is overwhelmingly not one.

## How it decides

The command is tokenised with `shlex` and split into command segments, so **`psql` is only ever
matched as a real command word**. `echo "psql -f supabase/migrations/x.sql"` is one command (`echo`)
with one opaque string argument, and does not match. `VAR=val` assignments and wrappers (`sudo`,
`env`, `timeout`, `nice`, …) are stepped over to find the real command word.

It matches:

- **`psql` naming a path under `supabase/migrations/`** — via `-f`, `--file=`, a `<` redirect, or a
  `\i` inside a quoted argument. Only paths inside that `psql` segment count, so a migrations path
  belonging to a different command on the same line is not attributed to it.
- **`supabase db push` / `supabase migration up`** — denied **always**: they never name a file, so
  nothing can be hashed. The house flow names the file.

Everything else exits 0 silently.

## Proving the ALLOW path, not just the deny

A hook that only ever refuses has not been shown to work. Two proofs.

**The lookup discriminates in both directions** — a string that IS on the relay is found, and one
that is not is not:

```
git grep -F "Chunk 3 — T0 preflight"  origin/main -- jahjah-internal/reports/   -> FOUND
git grep -F "SHA256: 0000…0000"       origin/main -- jahjah-internal/reports/   -> ABSENT
```

**End to end, through the real relay.** A throwaway fixture was written under
`supabase/migrations/`, hashed, and deleted; its hash is published by *this report*; the fixture is
then recreated byte-identically and put to the hook again, which must now allow it.

**The fixture is NOT a migration and no longer exists.** It is four lines of comment plus
`select 1;`, it was never committed, and `git status supabase/migrations/` is clean. Its hash is
recorded here only so the allow path could be exercised against the real `origin/main`:

SHA256: 7492f2f11b6ea2082b56b6464ae81bcb51205aa8fd188df14aadd94598eb07c5

Before this report was published, the hook refused that exact file:

```
GATE-1 hook: supabase/migrations/29999999999999_gate1_hook_allow_path_fixture.sql
sha256 7492f2f1… is not published on relay origin/main — publish the GATE-1 report carrying
"SHA256: 7492f2f1…" and push it first (D223/D228)
```

**Result after publication:** see the `ALLOW-PATH RESULT` section appended below.

## Note recorded in `docs/pitfalls/infra-vps.md`

A user-scope hook applies to **every** `claude` on this box, including the `web` tmux session that
works on the website project. The pattern only fires on `supabase/migrations/` paths, so the website
is untouched until it has migrations of its own — and when it does, the gate is wanted there too.

## ALLOW-PATH RESULT

The fixture was recreated **byte-identically** (`7492f2f1…` both times) and put to the hook again,
with the only change in the world being that this report is now on the relay's `origin/main`:

```
recreated fixture sha256: 7492f2f11b6ea2082b56b6464ae81bcb51205aa8fd188df14aadd94598eb07c5
expected:                 7492f2f11b6ea2082b56b6464ae81bcb51205aa8fd188df14aadd94598eb07c5
  -> byte-identical

--- hook AFTER the sha is published (expect ALLOW) ---
  exit=0
  stdout: (empty)
  stderr: (empty)
  log:    2026-09-02T15:53:57Z ALLOW   …29999999999999_gate1_hook_allow_path_fixture.sql
          sha256 7492f2f1…07c5 is published on relay origin/main
```

**Same file, same bytes, opposite verdicts — the only variable was publication.** That is the whole
mechanism, demonstrated rather than asserted.

The fixture was then deleted, and the hook refuses it again for the right reason:

```
--- fixture deleted; is supabase/migrations clean? ---
  CLEAN
--- and the hook now refuses it again (file gone) ---
GATE-1 hook: refused — …29999999999999_gate1_hook_allow_path_fixture.sql does not exist, so its
bytes cannot be hashed or checked against the relay (D228).
```

`git status` is clean; nothing from this test was committed, and the hashed file no longer exists,
so the published hash above can never authorise anything.
