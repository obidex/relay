## 4. Findings

**F1 — two `settings.local.json` allow rules do not match and were denied at use.** Both
`Bash(gh issue *)` and `Bash(systemctl list-timers *)` are listed under `allow`, and both commands were
**denied**:

```
gh issue view 72 --repo obidex/jahjah-internal --json ...   -> denied
systemctl list-timers 'jahjah*' --all                        -> denied
```

The working rules in `settings.json` all use the `:*` prefix form (`Bash(ls:*)` — which succeeded this
session); these two use a space-and-star form. **This is the same shape as trap 3 in
`docs/runbooks/automations.md` §4: a rule the engine accepts and then does not apply.** The difference
is that trap 3 was a *deny* rule that banned nothing; this is an *allow* rule that permits nothing —
strictly the safe direction, but it means the lane cannot read its own timer state or an issue's
metadata, and anyone reading the file would believe it can.

Suggested fix, for the owner or a session with `.claude/` in bounds — **not applied here, `.claude/` is
out of this job's bounds**:

```json
"allow": ["Bash(gh issue:*)", "Bash(systemctl list-timers:*)"]
```

**F2 — two non-enforcing allow rules remain in `.claude/settings.json`**, reported by the engine at
startup and captured in `stdout.log`:

- `Glob(**)` matches nothing — file permission checks read `Read(...)` rules, which already cover every
  file-reading tool.
- `Write(**)` matches nothing — file edit checks read `Edit(...)` rules, which already cover `Write`.

Neither weakens anything: `Read(**)` and `Edit(**)` are both present and do the work. They are dead
lines that invite the trap-3 misreading. Deleting them would leave a clean startup, which matters
because those warnings are the only place a mis-shaped rule ever surfaces.

**F3 — none.** No bound was hit, no destructive action was attempted, nothing was routed around.
