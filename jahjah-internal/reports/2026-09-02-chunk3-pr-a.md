## 1. `ci-ok` — the single required check

One aggregate job: `needs:` all seven other jobs, `if: always()`, fails on any `failure` or
`cancelled`, passes on `success` or `skipped`. Job id and display name are both exactly `ci-ok`.

**The verdict is read from the `needs` context, not from a hardcoded list** — a new job added to
`needs:` is covered with nothing else to remember. The one thing that must not be forgotten is the
`needs:` line itself, and `docs/runbooks/testing.md` §2 now says so in the job list.

`cancelled` fails on purpose: `concurrency.cancel-in-progress` cancels superseded runs, and a
cancelled run is not evidence of anything.

## 2. Dependabot — and a defect it would have shipped with

The config is exactly as specified: Actions + npm, weekly Monday 04:00 UTC, grouped, three open PRs
per ecosystem, labelled `deps` (label created), never auto-merged.

**Found in the reviewer pass, before merge: as written, every Dependabot PR would have been
permanently unmergeable.** GitHub passes **no Actions secrets** to a workflow triggered by
Dependabot — only Dependabot secrets exist in that context
([GitHub docs](https://docs.github.com/en/code-security/reference/supply-chain-security/dependabot-on-actions)).
So `SUPABASE_ACCESS_TOKEN` would be empty, `sql` and `e2e` would fail on authentication, `ci-ok`
would go red, and the new ruleset would refuse the merge — for ever, on every weekly PR.

**The fix is a skip, deliberately not a Dependabot secret.** Copying the Management API token into
Dependabot secrets would hand the live dev database to a workflow whose entire purpose is running a
dependency version nobody has reviewed yet. `sql` and `e2e` now carry
`if: github.actor != 'dependabot[bot]'`. The five secret-free jobs — `checks` (lint, types, unit
tests), `secret-scan`, `sast`, `types`, `replay`+grant-audit — still gate every bump, and they are
the jobs that can actually see a bad dependency.

**This is a deviation from the prompt's A1/A2 text** (which did not anticipate the interaction) and
the strategist can reverse it. It is recorded here because without it deliverable A2 is inert.

## 3. Grant audit (`D229`) — landed **BLOCKING**

`scripts/grant-audit.sh`, run by the `replay` job after the replay and the security postlude.

**How the reference list is built** — from the application source, never hand-kept:
`.from('x')` → relation (strict) · `.rpc('f')` → function, every overload (strict) · embed targets
inside `.select(…)` → relation (advisory: checked if it exists, since the extraction also catches
`!inner` and nested `.select(`).

**The embed lane is not decoration.** `sales_dispatch_items` is reached **only** as a PostgREST
embed. A `.from()`-only sweep would never look at it, and a missing SELECT grant there breaks the
dispatch dock exactly as hard.

**124 references checked: 57 relations, 64 RPCs, 3 embed-only.**

### Sabotage check — the evidence

Run in a live replay container, against the real end state:

```
=========== BASELINE ===========
== grant-audit: PASS — every referenced relation and RPC is explicitly granted to authenticated
exit=0

=========== revoke select on public.suppliers from authenticated ===========
### FAIL  grant-audit: 1 reference(s) the application uses are NOT reachable by authenticated:
    NOGRANT  relation  from   suppliers (INSERT,UPDATE,DELETE)
exit=1

=========== also revoke execute on stock_on_hand from authenticated ===========
### FAIL  grant-audit: 2 reference(s) the application uses are NOT reachable by authenticated:
    NOGRANT  function  rpc    stock_on_hand (p_variant_ids uuid[])
    NOGRANT  relation  from   suppliers (INSERT,UPDATE,DELETE)
exit=1

=========== restored ===========
== grant-audit: PASS
exit=0
```

The `suppliers (INSERT,UPDATE,DELETE)` detail is the useful part: it says the table still holds its
write grants and lost only SELECT, which is the shape a forgotten `grant select` actually leaves.

**And it ran for real in CI** — [replay job](https://github.com/obidex/jahjah-internal/actions/runs/33646282372),
110 `ok` steps then `== grant-audit: 124 reference(s) checked … PASS`. The job's 47s runtime was
checked rather than assumed; the log shows every migration and seed applying.

### The replay-vs-live diff — **empty**, and that is the finding

The same audit was run once against the **live dev database**, read-only
(`begin; set transaction read only; … ; rollback;`), over this box's direct `psql` lane.

- **Zero status differences** across all 124 references.
- **Zero privilege-set differences** — the full `SELECT/INSERT/UPDATE/DELETE` set matches on every
  one of the 60 relations.
- A **widened sweep of every `public` relation** (not just app-referenced): **63 in replay, 63
  live, identical names, identical `authenticated` and `anon` ACLs** across all seven privilege
  types.

**So: no app-referenced relation — and in fact no `public` relation at all — is living on platform
auto-grants.** The house pattern from `CLAUDE.md` §6 (`revoke all …` then grant explicitly) has been
applied consistently enough that a from-scratch build reproduces live exactly.

**Nothing to fix, so nothing is carried into chunk 4 from this.** `D229`'s roadmap close-trigger
("any app-referenced relation the grant audit finds ungranted") resolves to **none**. The gate is
still worth having: it is what makes the next forgotten grant a red build instead of a launch-day
outage.

*(One caveat kept honest: the first version of the widened sweep failed on an uncast `relkind` and
the diff still printed "0 differing". That is the green-proves-nothing trap; the numbers above come
from the fixed query, which reports 63/63 rather than 0/0.)*
